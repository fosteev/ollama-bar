# ollama-bar — план реализации

## Цели

Дать локальному серверу Ollama наблюдаемость, которой у него сейчас нет:

- какие модели загружены, сколько они стоят по памяти и когда будут выгружены
- с какой скоростью идёт генерация прямо сейчас
- что модель на самом деле выдаёт — включая запросы, которые инициировало не это приложение

## Не цели

- Управление моделями (pull/delete/create). CLI `ollama` уже делает это хорошо.
- Чат-UI. Это монитор, а не клиент.
- Удалённый или мультихостовый Ollama. Только localhost, по крайней мере пока локальный случай не доведён.
- Учёт квот и биллинга хостовых провайдеров. Это работа ClaudeBar.

## Архитектура

Два независимых потока данных. Они намеренно развязаны: поллер полезен сам по себе,
а прокси — та часть, которую можно отложить.

```
                    ┌──────────────┐
   agent client ───►│  proxy :11435│───► ollama :11434
   (codex, etc.)    └──────┬───────┘          │
                           │ bodies           │ /api/ps, /api/tags
                           │ + SSE frames     │ server.log
                           ▼                  ▼
                    ┌─────────────────────────────┐
                    │        OllamaBarCore        │
                    │  inventory · timings · IO   │
                    └──────────────┬──────────────┘
                                   ▼
                          menu bar UI (SwiftUI)
```

### Путь A — поллер (без перехвата)

Опрашивает HTTP API Ollama и читает хвост серверного лога. Покрывает инвентарь, память и
пропускную способность. Не требует никаких изменений конфигурации на стороне клиента.

### Путь B — прокси (перехват)

Реверс-прокси, слушающий `:11435` и форвардящий на `:11434`, записывающий тела запросов и
ответов и пересобирающий SSE-поток. Клиенты перенастраиваются на порт прокси.

Это единственный общий способ увидеть вывод. Ollama не предоставляет интерфейса для наблюдения
за чужим стримом, а серверный лог несёт только метаданные, никогда не содержимое. Чтение логов на
стороне клиента (например, session rollouts Codex в `~/.codex/sessions/`) работает, но требует
отдельной реализации под каждый клиент и покрывает только те клиенты, которые пишут структурные
логи — приемлемо как запасной вариант, но не как основа дизайна.

## Источники данных

Всё нижеперечисленное проверено на Ollama 0.32.6 под macOS.

### `GET /api/ps` — загруженные модели

```json
{
  "name": "qwen3.5-27b-32k:latest",
  "size": 18256861592,
  "size_vram": 18256861592,
  "context_length": 32768,
  "expires_at": "2026-08-06T12:22:28+03:00",
  "details": {
    "parameter_size": "27.8B",
    "quantization_level": "Q4_K_M",
    "family": "qwen35"
  }
}
```

Всё, что нужно вью с инвентарём, в одном вызове. `expires_at` даёт обратный отсчёт до выгрузки;
`size_vram` против `size` показывает, целиком ли модель лежит на GPU.

Замечено на живом сервере: выгрузка ленивая — модель продолжает числиться в `/api/ps` уже после
наступления `expires_at`. Отрицательный отсчёт означает «выгрузка назрела», а не «модели больше
нет», и UI должен показывать именно это.

### `GET /api/tags` — установленные модели

Инвентарь на диске: что можно загрузить без скачивания.

### `~/.ollama/logs/server.log` — тайминги

llama.cpp пишет строки по слотам:

```
slot print_timing: id 0 | task 4611 | n_decoded = 116, tg = 5.22 t/s, tg_3s = 5.30 t/s
slot create_check: id 0 | task 4611 | created context checkpoint 3 of 32 (n_tokens = 22613, size = 149.626 MiB)
[GIN] 2026/08/06 - 12:17:53 | 200 | 136.625µs | 127.0.0.1 | GET "/api/ps"
```

`tg` — токены генерации в секунду, `tg_3s` — короткое скользящее среднее. Строки GIN дают тайминг и
статус на уровне запроса. Парсинг — построчные регулярки по хвосту файла.

Собственный поллинг приложения попадает в тот же access-лог и ничем не отличим от чужого трафика:
при опросе раз в секунду `/api/ps` и `/api/tags` полностью забивают историю запросов. Поэтому
`/api/tags` опрашивается редко (раз в 30 секунд — список на диске меняется только при pull/delete),
а записи по обоим эндпоинтам помечаются как свои и по умолчанию скрыты из истории.

Особенности формата, проверенные на живом логе:

- Имя операции llama.cpp обрезает по фиксированной ширине, поэтому в файле лежат `slot
  get_availabl:` и `slot launch_slot_:` вместо полных имён. Матчить нужно по префиксу.
- Числовые поля выровнены пробелами (`id  0`, `tg =   5.76 t/s`) — пробелов произвольное
  количество.
- Реально встречающиеся типы строк: `print_timing`, `create_check`, `launch_slot_`,
  `get_availabl`, `init_sampler`. Интерес представляют первые две.

Ротацию лога нужно обрабатывать — переоткрывать файл при смене inode.

### Тела, снятые прокси

`POST /api/chat`, `/api/generate`, а также OpenAI-совместимые `/v1/chat/completions` и
`/v1/responses`. Стриминговые ответы приходят как SSE или как JSON, разделённый переводами строк, —
в зависимости от эндпоинта; и то и другое требует инкрементального парсинга, чтобы частичный вывод
был виден ещё до завершения генерации.

## Фичи

Отсортированы по отношению пользы к трудозатратам.

1. **Загруженные модели** — имя, параметры, квантизация, резидентный размер, выделенный контекст, обратный отсчёт до выгрузки.
2. **Пропускная способность** — живые токены/сек с привязкой к модели.
3. **История запросов** — клиент, модель, эндпоинт, счётчики токенов промпта и ответа, длительность, статус.
4. **Живой вывод** — текст ответа и tool calls по мере генерации.
5. **Предупреждение о несовпадении контекстного окна** — см. ниже.
6. **Уведомления про простой и выгрузку** — модель загружена, выгружена или заменена.

### Предупреждение о несовпадении контекстного окна

Клиент, который не знает реальное контекстное окно модели, не будет компактить диалог, а Ollama
молча обрежет промпт при переполнении — агент после этого забывает собственные инструкции, и нигде
нет никакой ошибки.

Это наблюдаемо: `/api/ps` отдаёт реальный `context_length`, а прокси видит промпт, который клиент
реально отправляет. Когда размер промпта подбирается к выделенному окну — предупреждать. Сигнал
действительно полезный и получается бесплатно из уже собираемых данных.

## Структура проекта и тулинг

За основу взята раскладка [ClaudeBar](https://github.com/tddworks/ClaudeBar) — тот же класс
приложения (macOS 15+, `MenuBarExtra`, Swift 6, слоистая архитектура), проверенная на живом проекте.

### Раскладка

```
Package.swift              # SPM: Core, Infrastructure, CLI
Project.swift              # Tuist: таргет .app (появляется на M2)
Sources/
  Core/                    # OllamaBarCore: модели, OllamaMonitor, протоколы
  Infrastructure/          # API-клиент, тейлер лога, парсеры, прокси, хранилище
  CLI/                     # ollama-bar-cli
  App/                     # SwiftUI: MenuBarExtra, вью, настройки (M2)
Tests/
  CoreTests/
  InfrastructureTests/
  AcceptanceTests/
Fixtures/                  # снятые куски server.log и ответы API
docs/
scripts/
```

Зависимости строго в одну сторону: App → Infrastructure → Core. `Core` не знает ни про сеть, ни
про файловую систему — только модели, состояние и протоколы; всё I/O живёт в `Infrastructure` и
подставляется через протоколы. На обоих `SWIFT_STRICT_CONCURRENCY: complete`.

### Сборка

Логика — обычный SPM-пакет, приложение — Tuist поверх него:

```bash
swift build && swift test          # M1: ядро и CLI, без Xcode
swift run ollama-bar-cli

brew install tuist                 # M2 и дальше
tuist install && tuist generate
```

Tuist нужен ради `.app`-таргета, ассетов, entitlements и `ENABLE_DEBUG_DYLIB` для превью SwiftUI —
то есть только с M2. Тащить его в M1 смысла нет: headless-ядро с тестами — ровно то, что SPM умеет
из коробки, а `swift test` выполняется без генерации Xcode-проекта. Когда появится `Project.swift`,
он будет зависеть от локального пакета через `.package(path: ".")`, раскладка исходников не
меняется. Сгенерированные `*.xcodeproj` / `*.xcworkspace` — в `.gitignore`.

### Единый источник правды

`OllamaMonitor` (`Core`) владеет всем состоянием — инвентарь, тайминги, история запросов — и
публикуется через `@Observable`. Вью подписываются на него напрямую, без слоя ViewModel и без
глобального AppState. Из ClaudeBar берётся именно эта идея (`QuotaMonitor`), но не его модель
обновления: у них интервальный рефреш квот, у нас Путь A поллит, а Путь B — настоящий стрим,
который пушит события по мере их появления.

Чего из ClaudeBar сознательно не берём: иерархию provider-репозиториев по ISP (она выросла из
двух десятков провайдеров с разными конфигами — у нас один бэкенд, плодить протоколы не под что),
систему тем, LiveActivity, SwiftTerm.

### Тесты

Протокол-ориентированный DI, моки через `@Mockable`. Тесты проверяют изменения состояния, а не
факты вызова методов. Три таргета соответствуют слоям; парсеры лога и SSE тестируются на
записанных фикстурах — реальные куски `server.log` и настоящие стримы, снятые прокси.

### Логирование

Двойной вывод по образцу `AppLog` из ClaudeBar: OSLog для разработки (Console.app, фильтр по
subsystem) плюс файл в `~/Library/Logs/ollama-bar/` с ротацией — для пользователей. Уровень
`debug` идёт только в OSLog. Категории: `monitor`, `poller`, `logtail`, `proxy`, `ui`,
`notifications`. Для прокси файловый лог понадобится буквально на второй день отладки.

### Настройки

Один JSON-файл `~/.ollamabar/settings.json` с ключами через точку (`app.pollInterval`,
`ollama.host`, `proxy.enabled`, `proxy.port`) вместо россыпи по UserDefaults.

## Строка меню-бара

Решение принимается здесь, потому что от него зависит форма публикуемого состояния в `Core`, а не
только вёрстка на M2.

Принцип: **текст появляется, только когда что-то происходит.** Постоянная надпись в меню-баре —
это шум, который пользователь перестаёт замечать через день.

| Состояние | Что видно |
|---|---|
| Ollama не отвечает | приглушённая иконка, без текста |
| Модели не загружены | обычная иконка, без текста |
| Модель загружена, простаивает | иконка + точка-индикатор; счётчик выгрузки только в поповере |
| Идёт генерация | иконка + `5.8 t/s` |

Цифры — моноширинные (`.monospacedDigit()`), иначе ширина строки прыгает на каждом обновлении и
дёргает соседние иконки меню-бара.

Что это значит для `Core`:

- Монитор публикует `MenuBarState` — маленький тип, отдельный от полного состояния, чтобы вью в
  меню-баре не перерисовывалось на каждое изменение инвентаря.
- Генерация — состояние с таймаутом, а не событие: пока строки `print_timing` продолжают приходить,
  считаем, что идёт генерация; после 2 секунд тишины гасим показатель. Ollama не сообщает о
  завершении генерации в лог явно, так что это единственный доступный признак.
- Значение t/s берётся из `tg_3s` (скользящее среднее), а не из `tg` — мгновенное значение слишком
  дёргается, чтобы на него можно было смотреть.

Поповер: список загруженных моделей (имя, параметры, квантизация, резидентный размер, VRAM/RAM,
контекст, обратный отсчёт до выгрузки), под ним пропускная способность, ниже — история запросов
(с M3). Детальная вёрстка — по ходу M2.

## Вехи

### M0 — разведка (одноразовая)

Скрипты на shell + `jq`, которые дёргают `/api/ps`, читают хвост `server.log` и печатают поля выше.
Подтверждают, что источники данных всё ещё ведут себя как описано, до того как написана хоть строчка
Swift. Не шипается, не сохраняется.

**Готово, когда:** однострочник в терминале показывает загруженные модели и живые t/s.

**Статус: сделано.** Источники подтверждены на Ollama 0.32.6, снятые образцы лежат в `Fixtures/`
и используются как фикстуры тестов.

### M1 — ядро, без UI

Swift-пакет `OllamaBarCore`:

- API-клиент для `/api/ps`, `/api/tags`
- тейлер лога с обработкой ротации и парсер таймингов
- модель текущего состояния в памяти, публикуемая для наблюдателей

Шипается как CLI (`ollama-bar-cli`), печатающий состояние по интервалу. Без UI, полностью покрывается
юнит-тестами на записанных фикстурах.

**Готово, когда:** CLI корректно показывает загруженные модели и t/s во время реального прогона
агента, а парсеры покрыты тестами на снятых кусках лога.

**Статус: сделано.** `swift test` — 30 тестов, включая ротацию лога и разорванные строки. На живой
генерации CLI показывал 5.4 → 6.5 t/s и гасил показатель через 2 секунды после её окончания.

### M2 — приложение в меню-баре

SwiftUI `MenuBarExtra` (macOS 15+), рендерящий состояние из M1. Список инвентаря, пропускная
способность, обратный отсчёт до выгрузки. Настройки интервала опроса и хоста/порта Ollama.

**Готово, когда:** приложение живёт в меню-баре и полезно без терминала.

**Статус: сделано.** `MenuBarExtra` в режиме `.window`, панель с загруженными моделями, живым
t/s и историей запросов, настройки хоста/интервала/пути к логу в JSON-файле. Мониторинг стартует
вместе с приложением, а не при открытии панели — иначе меню-бар не показывал бы скорость, пока
пользователь не кликнет.

### M3 — прокси и живой вывод

Реверс-прокси на SwiftNIO на настраиваемом порту. Пропускает поток без изменений, записывает тела,
инкрементально парсит SSE/NDJSON, кормит историю запросов и вью живого вывода. Обязан быть
прозрачным: клиент, говорящий с прокси, ведёт себя ровно так же, как если бы говорил с Ollama —
включая задержки стриминга, ошибки и отмену.

**Готово, когда:** полный прогон агента Codex через порт прокси завершается с идентичным
результатом, а его вывод виден в приложении вживую.

### M4 — полировка

Персистентность истории между запусками, уведомления, предупреждения о несовпадении контекста,
темы.

## Технические решения

**Swift от начала до конца.** Прокси на Go написался бы быстрее, но это значит таскать с собой
сайдкар-бинарь и поддерживать два тулчейна ради одного маленького приложения. SwiftNIO для
localhost-прокси более чем достаточно.

**macOS 15+, SwiftUI `MenuBarExtra`.** Никакой возни с меню-баром на AppKit, никаких сторонних
UI-зависимостей.

**Tuist для генерации проекта.** См. «Структура проекта и тулинг».

**Прокси опционален.** Приложение полностью работоспособно без него. Включение перехвата — явное
действие пользователя, поскольку требует перенастройки клиентов.

**Без демона.** Всё живёт в процессе приложения. Если приложение не запущено — ничего не пишется;
для монитора это приемлемо.

## Открытые вопросы

- Должен ли прокси по умолчанию вставать на свой порт — или занимать `:11434`, переселяя Ollama?
  Занятие стандартного порта сделало бы перехват прозрачным для клиентов, но драка с приложением
  Ollama за порт — хрупкая затея. Начинаем с явного второго порта.
- Сколько истории вывода держать в памяти до сброса на диск, учитывая, что ответы бывают большими,
  а слотов может работать несколько одновременно.
- Парсить ли JSONL rollout'ов Codex как zero-config запасной вариант для вывода до появления M3 —
  или сразу считать это тупиком.

## Риски

- **Формат лога — не API.** Строки `slot print_timing` — это внутренности llama.cpp, они могут
  меняться между релизами Ollama. Парсеры должны деградировать мягко: потерять отображение
  пропускной способности, но никогда не падать.
- **Кривой прокси хуже, чем отсутствие прокси.** Тонко сломанный прокси портит реальные прогоны
  агентов. До того как через него пойдёт живая работа, нужен набор тестов на прозрачность.
- **Расползание скоупа в сторону чат-клиента.** Как только начнёт рендериться живой вывод, появится
  соблазн добавить поле ввода. Это вне скоупа.
